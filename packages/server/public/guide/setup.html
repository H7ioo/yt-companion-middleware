YouTube Live Middleware · v2

Get it running, and
know why it has no login.

Install and start the middleware, then understand the trust model it assumes: a private LAN, where the dashboard and every endpoint are open to anyone who can reach the port.

02 Install & run

Node 20+, one OAuth refresh token, a JSON file on disk. That's the whole footprint.

Configure the environment

Copy .env.example to .env and fill it in. The YouTube refresh token is obtained once through Google's OAuth consent flow and stays server-side — it is never exposed to Companion or any browser. 

# YouTube OAuth 2.0 (Google Cloud Console → OAuth client)
YT_CLIENT_ID=your-client-id.apps.googleusercontent.com
YT_CLIENT_SECRET=your-client-secret
YT_REFRESH_TOKEN=your-refresh-token

PORT=8080
DATA_DIR=./data            # JSON store; mount as a Docker volume
REFRESH_INTERVAL_SECONDS=60
HEALTH_FAILURE_THRESHOLD=3   # fails in a row before health escalates
YT_REGION_CODE=US            # drives the assignable category list
YT_QUOTA_LIMIT=10000          # daily quota budget, shown on the dashboard

Run it

# development — API on :8080 (tsx watch, auto-restart)
npm install
npm run dev

# hot-reloading dashboard (separate terminal, Vite dev server)
npm --prefix web run dev

# production — build the SPA + server, then serve both from :8080
npm run build:all
npm start

npm run dev runs the API only. In development the dashboard is served by Vite on its own port (proxying /api and /guide back to :8080); the production build bundles the SPA so npm start serves everything from a single port.

Open http://<host>:8080 for the dashboard, /docs for the interactive API console, and this page at /guide. The API lives under /api.

Storage. Presets, default settings, the webhook URL, and cached state all live in a single JSON file under DATA_DIR. Writes are atomic (temp file, then rename) so a crash mid-write can't corrupt it. Mount that directory as a Docker volume and your config survives redeploys.

Connecting YouTube on a hosted deployment

A headless host has no browser for the server to open, so the desktop build's one-click connect cannot run there. Set PUBLIC_ORIGIN to the origin this server answers on and the dashboard gains a browser sign-in instead: it sends your browser to Google, and Google returns it to the server's callback. Nobody has to run scripts/get-refresh-token.mjs or paste a refresh token by hand. 

# The full origin, scheme included, no trailing path.
PUBLIC_ORIGIN=https://live.example.org

Then register the callback below as an Authorized redirect URI on the OAuth client in the Google Cloud Console. It is matched character for character — a mismatch fails at the consent screen with redirect_uri_mismatch, not at boot. 

https://live.example.org/api/setup/oauth/callback

The dashboard shows the exact string for this deployment on the setup screen and in Settings → YouTube connection, so it can be copied rather than retyped. On success the refresh token is stored server-side and the YouTube client is rebuilt in-process — no restart, and Companion's connection stays up.

This is where the client secret becomes a real secret. Unlike the bundled desktop client, a hosted deployment's OAuth client lives only on the server. Connecting is admin-only, and nothing about the credentials is ever read back to a browser — status answers in booleans.

Leave PUBLIC_ORIGIN unset for desktop, LAN and direct Docker installs. Without it the connection is still replaceable from Settings, but by pasting a token minted with node packages/server/scripts/get-refresh-token.mjs.

If the round trip cannot be made to work — Google refuses the redirect URI, or a Workspace policy blocks the app — the paste form is still there behind “Google won’t send me back here”, on the setup screen and in Settings. Mint a token with node packages/server/scripts/get-refresh-token.mjs on any machine that has a browser and enter all three values.

Either way the connect is recorded in the audit log: starting a browser sign-in, and the callback that actually changed the credentials, both name the admin who did it.

03 No login (LAN-trust)

There is no token, no header, no login screen. Anything on your LAN can trigger the app — and that is the intended design.

The threat model is a personal tool on a private network: the worry is a random device on the same LAN casually hitting an endpoint, not a determined attacker. If someone already has access to this host, API auth wouldn't have saved you anyway. So the Bearer token from earlier versions is gone — no Authorization header to set in Companion, nothing to regenerate.

Do not port-forward this to the internet. Every action and feedback endpoint is unauthenticated. Keep it on the LAN (or behind a VPN) and you're within the model; expose it publicly and anyone can rewrite your broadcast.

The action endpoints answer on two bases, split by caller: /api/action/* is the Companion base and /api/dashboard/action/* is the dashboard base. Both run the same handler and are intentional — use whichever fits the caller; both are supported.

LAN-only. No auth. Keep it off the open internet.
